# AICMS — архітектура

> CMS, у якій AI-агенти — повноправні користувачі, а людина — редактор і власник.
> Опиши модель один раз і отримаєш REST, MCP-інструменти, адмінку й типи.

Статус: v0.4 · фаза 3 працює: Postgres, Cloudflare Workers з D1 і R2, присутність наживо, реєстр модулів, A2A і commerce поверх фаз 0–2 · [English](ARCHITECTURE.md)

---

## 1. Навіщо

WordPress виріс із блогу 2003 року: тисячі файлів ядра, `wp_posts` + `wp_postmeta` замість схем, глобальні хуки з пріоритетами, REST, доданий пізніше, і адмінка, яку агентам доводиться «скрейпити». Агентам потрібне інше:

- **явні схеми**, щоб знати, що можна писати;
- **типізовані інструменти** замість HTML-форм;
- **межі прав**, щоб агент не міг зробити зайвого;
- **чернетки й відкат**, щоб помилка агента нічого не ламала.

AICMS будується навколо цих чотирьох потреб. Людина отримує ту саму систему через Studio, тому їй теж простіше.

## 2. Принципи

1. **Одна схема — усе інше генерується.** Модель описується в TypeScript один раз. З неї виходять таблиці, валідація, REST, MCP-інструменти, форми Studio, типи для фронтенду й документація для агентів.
2. **Кожна дія — це Action.** Створити запис, згенерувати alt-текст, провести SEO-аудит: одна сутність з input/output-схемою, правами й хуками. Входи (MCP, REST, SDK, Studio) лише викликають Actions.
3. **Агент не пише в прод напряму.** Зміни агента потрапляють у changeset, проходять перевірки й рев'ю, і лише тоді публікуються. Кожна подія лягає в журнал, тому будь-що відкочується.
4. **Модуль — одна папка, один файл-маніфест.** Модуль оголошує, що він дає (`provides`) і що йому потрібно (`requires`). Ніякої глобальної каші з хуків.
5. **Мінімум файлів.** Проєкт — це `aicms.config.ts`, папка `models/` і, за потреби, `modules/`. Усе згенероване лежить у `.aicms/` і не комітиться.
6. **Headless, але з першокласними адаптерами.** Next.js, Nuxt, SvelteKit, Astro, React Router, Angular, Expo: типізований клієнт, live preview, ревалідація кешу.
7. **Веб-стандарти.** Ядро працює на `Request/Response`, тому запускається на Node, Bun, Deno і Cloudflare Workers.

## 3. Словник: сім понять

| Поняття | Що це | Приклад |
|---|---|---|
| **Model** | Схема типу контенту разом з інструкціями для агентів | `post`, `product`, `review` |
| **Entry** | Один запис моделі з історією версій | «Як обрати SPF на зиму» |
| **Block** | Цеглинка в rich-контенті | `paragraph`, `image`, `cta` |
| **Action** | Будь-яка операція з типізованим входом, виходом і правами | `post.draft`, `seo.audit` |
| **Module** | Пакет із моделями, блоками, Actions, хуками й панелями Studio | `seo`, `commerce`, `reviews` |
| **Agent** | Ідентичність агента з правами, бюджетом і режимом рев'ю | `writer`, `seo`, `moderator` |
| **Changeset** | Набір запропонованих змін, що чекає перевірки й рев'ю | «writer: 3 нові статті» |

Більше вчити нічого не треба.

## 4. Шари системи

```
┌──────────────────────────────────────────────────────────────┐
│  Агенти (Claude, GPT, Gemini, власні)      Люди (Studio)       │
└───────────────┬──────────────────────────────────┬───────────┘
                │                                  │
┌───────────────▼──────────────────────────────────▼───────────┐
│  ВХОДИ   MCP · REST+OpenAPI · GraphQL · SDK · Events · A2A      │
│          (усі генеруються з реєстру Actions)                    │
└───────────────┬──────────────────────────────────────────────┘
                │ виклик Action
┌───────────────▼──────────────────────────────────────────────┐
│  ЯДРО                                                          │
│   Schema Engine → Action Bus → Policy (scopes, бюджети, рев'ю)  │
│   Content Store (entries, versions, changesets, event log)      │
│   Module Loader (provides / requires, ізоляція)                 │
└───────┬───────────────────────────────┬──────────────────────┘
        │                               │
┌───────▼─────────┐            ┌────────▼───────────────────────┐
│  МОДУЛІ         │            │  АДАПТЕРИ                        │
│  seo, i18n,     │            │  БД: SQLite · Postgres · libSQL  │
│  media, search, │            │  Медіа: local · S3 · R2          │
│  commerce, …    │            │  Вектор: sqlite-vec · pgvector   │
└─────────────────┘            └────────────────────────────────┘
```

### 4.1 Schema Engine
- Читає моделі з `models/*.ts` і з модулів.
- Видає JSON Schema кожної моделі й кожного Action, OpenAPI, маніфест для агентів і `llms.txt`. Типи TypeScript: у проєкті CMS вони виводяться прямо з моделі (`InferModel<typeof post>`); фронтенд в іншому репозиторії отримує їх командою `aicms types`, а `@aicms/client` приймає їх як параметр типу.
- Валідація на Zod 4 (реалізація Standard Schema), тому одна схема працює і на сервері, і в браузері.

### 4.2 Action Bus
- Реєстр усіх Actions: Actions ядра (`cms.describe`, `cms.submit`…), чотири згенеровані на кожну модель (`post.list`, `post.get`, `post.draft`, `post.delete`) і Actions модулів.
- Кожен виклик проходить один конвеєр:
  `валідація → перевірка прав → бюджет → виконання → журнал → подія`.
- Будь-який вхід (MCP, REST, CLI, Studio) — тонка обгортка над цим конвеєром. Тому поведінка однакова для людини й агента.

### 4.3 Policy
- **Scopes:** `post:read`, `post:draft` (створення + зміна), `post:update.seo` (одне поле), `post:delete`, `post:*`, `changesets:review`, `agents:manage`, `events:read`, `*`. Actions модулів оголошують власні scopes, наприклад `reviews:write`.
- **Схеми інструментів до рівня поля:** інструмент чернетки містить лише ті поля, які агенту дозволено змінювати. З `post:update.seo` інструмент `post_draft` має тільки `id` і `seo`.
- **Режим рев'ю** для кожного агента: `human` (людина схвалює) або `auto` (мерджиться, якщо всі перевірки зелені й жодна модель не вимагає людини). За замовчуванням `human`.
- **Останнє слово за моделлю:** якщо в `agent.can` моделі немає `publish`, будь-який changeset агента, що її зачіпає, чекає людину незалежно від режиму рев'ю агента.
- **Бюджети:** `actionsPerHour` і `maxChangesetItems`.
- **Kill switch:** `aicms agent revoke <name>` відкликає токени агента і відхиляє всі його незмерджені changesets.

### 4.4 Content Store
Шість таблиць ядра незалежно від кількості моделей:

| Таблиця | Призначення |
|---|---|
| `entries` | поточний стан: `id, model, locale, data (JSON), version` |
| `versions` | незмінна історія кожного запису |
| `changesets` | гілки змін від агентів і людей |
| `events` | журнал усіх Actions: хто, що, коли, через який вхід |
| `media` | файли, метадані, alt-тексти |
| `tokens` | токени агентів, лише як SHA-256 хеші |

Поля з `indexed: true` або `unique: true` отримують індекси на виразах (`json_extract(data, '$.slug')` у SQLite, `data->'slug'` на JSONB у Postgres). Модулі тримають невеликі значення в таблиці `kv`; модуль search має власний індекс термінів.

Один інтерфейс `Store`, три адаптери, і весь набір тестів проганяється на кожному:

| `db:` | Де | Примітки |
|---|---|---|
| `sqlite(".aicms/data.db")` | сервери, за замовчуванням | `node:sqlite`, нічого не треба ставити |
| `postgres({ url })` | сервери | JSONB; `npm install pg`; злиття в одній транзакції з блокуванням рядків |
| `d1("DB")` | Cloudflare Workers | злиття спершу плануються, потім застосовуються одним атомарним batch; первинний ключ версій ловить конкурентні зміни |

### 4.5 Module Loader
- Модулі підключаються в `aicms.config.ts`.
- Граф `requires → provides` перевіряється при старті й при `aicms add`.
- Модуль бачить лише свої моделі й ті, що явно перелічив у `uses`. Права модуля показуються при встановленні, як у застосунків на телефоні.

## 5. Структура проєкту

```
my-site/
├── aicms.config.ts      # БД, мови, модулі, агенти
├── models/
│   ├── post.ts
│   └── tag.ts
├── modules/             # необов'язково: власні модулі
│   └── reviews/
│       └── module.ts
└── .aicms/              # згенероване: база, кеш (у .gitignore)
```

### 5.1 Конфіг

```ts
// aicms.config.ts
import { defineConfig, sqlite } from "aicms"

export default defineConfig({
  db: sqlite(".aicms/data.db"),            // postgres() з'явиться у фазі 3
  locales: ["uk", "en"],
  public: ["post:read", "tag:read"],       // що можна анонімним запитам
  agents: {
    writer:    { scopes: ["post:draft", "tag:draft"], review: "human" },
    seo:       { scopes: ["post:update.seo"],         review: "auto"  },
    moderator: { scopes: ["reviews:write"], budget: { actionsPerHour: 500 } },
  },
  webhooks: [{ url: "https://my-site.ua/api/revalidate", events: ["changeset.merged"] }],
})
```

Моделі підвантажуються з `models/` автоматично; щоб перелічити їх явно, передай `models: [...]`.

### 5.2 Модель

```ts
// models/post.ts
import { defineModel, field } from "aicms"

export default defineModel({
  name: "post",
  label: "Статті",
  fields: {
    title:       field.text({ required: true, max: 120 }),
    slug:        field.slug({ from: "title" }),          // унікальний та індексований за замовчуванням
    cover:       field.media(),
    body:        field.blocks(["paragraph", "heading", "image", "quote", "cta"]),
    tags:        field.ref("tag", { many: true }),
    publishedAt: field.date({ indexed: true }),
  },
  agent: {
    guide: "Пиши коротко, тон дружнього експерта. Без кліше й води.",
    can: ["create", "update"],              // публікація лишається за людиною
  },
})
```

Slug з кириличного заголовка транслітерується за офіційною таблицею: «Як обрати SPF на зиму» → `yak-obraty-spf-na-zymu`.

Блок `agent` — ключова відмінність від класичних CMS: інструкції для агента живуть поруч зі схемою. Агент отримує їх разом зі списком інструментів.

## 6. Модулі: як Lego

### 6.1 Анатомія модуля

```ts
// modules/reviews/module.ts
import { defineModule, defineModel, field, action } from "aicms"

export default defineModule({
  name: "reviews",
  provides: ["reviews"],
  requires: ["commerce"],                // будь-яка реалізація commerce
  uses: ["product"],                     // чужі моделі, до яких є доступ

  models: [
    defineModel({
      name: "review",
      fields: {
        product: field.ref("product"),
        rating:  field.number({ min: 1, max: 5, required: true }),
        text:    field.text(),
        status:  field.enum(["pending", "published", "rejected"]),
      },
    }),
  ],

  actions: {
    moderate: action({
      description: "Схвалити або відхилити відгук",
      scope: "reviews:write",
      input: { id: field.id({ required: true }), ok: field.boolean({ required: true }) },
      run: ({ input, ctx }) =>
        ctx.draft("review", { id: input.id, status: input.ok ? "published" : "rejected" }),
    }),
  },

  on: {
    "changeset.merged": ({ payload, ctx }) => { /* сповістити, переіндексувати… */ },
  },
})
```

Усередині `run` об'єкт `ctx` пише через changeset того, хто викликав Action, тому модуль ніколи не обійде рев'ю. Читання враховує чернетки цього ж агента, тож модуль може перевірити роботу ще до сабміту.

Модуль також може мати:

| Частина | Що робить | Приклад |
|---|---|---|
| опції | модулі зазвичай фабрики: `seo({ siteUrl })` | `aicms.config.ts` |
| `setup(ctx)` | виконується раз під час старту чи встановлення | побудувати індекс |
| `services` | реалізація можливості з `provides` | `search` відповідає за `cms.search` |
| `routes` | HTTP-маршрути `"GET /sitemap.xml"` з `:params` | `/media/:id/:name` |
| `ctx.kv` | невеликі JSON-значення модуля | групи перекладів |
| `ctx.pending(id)` | чиясь неопублікована чернетка запису | «вже чекає рев'ю» |

Усе, що модуль просить, видно в його маніфесті (`cms_modules`, `aicms modules`, Studio): моделі, які він додає й використовує, Actions зі scopes, маршрути й хуки. Модулі можна встановлювати в запущений сервер: їхні інструменти, маршрути й типи GraphQL з'являються одразу.

```bash
aicms add seo                 # офіційний модуль
aicms add ./modules/reviews   # локальна папка
aicms add @someone/aicms-x    # npm-пакет (npm install + конфіг)
aicms module new reviews      # заготовка modules/reviews/module.ts
aicms remove seo              # дані лишаються в базі
```

`aicms add` дописує імпорт і запис у `modules`, підтягує офіційні модулі, які дають потрібні новому можливості, перевіряє, що проєкт і далі стартує, а якщо ні — повертає файл як був.

### 6.2 Можливості замість залежностей від пакетів

| `requires` | Хто може надати (`provides`) |
|---|---|
| `payments` | `liqpay`, `monobank`, `stripe`, `paddle` |
| `shipping` | `nova-poshta`, `ukrposhta`, `dhl` |
| `search` | `search-sqlite`, `search-pg`, `meilisearch` |
| `ai.image` | `openai-images`, `flux`, `local-sd` |

Тому модулі міняються без переписування решти.

### 6.3 Офіційні модулі

Зроблено у фазі 2 (`import { seo, search, media, i18n, gitSync } from "aicms/modules"`):

| Модуль | Що дає агентам і людям |
|---|---|
| `seo` | `seo_audit`: оцінка 0–100 з конкретними правками (довжина заголовка й опису, slug, кількість слів, порядок заголовків, alt зображень, внутрішні посилання), працює з чернетками; `seo_report` для всієї моделі; `sitemap.xml` і `robots.txt` |
| `search` | повнотекстовий пошук будь-якою мовою з ранжуванням (TF-IDF, вага заголовка, пошук за префіксом) на переносному індексі; `cms_search` переходить на нього одразу після встановлення |
| `media` | медіатека: завантаження, імпорт за URL (приватні мережі заблоковано), розміри зображень, alt-текст, який може дописати агент, безпечний SVG, файли під `/media` |
| `i18n` | групи перекладів між мовами, чого бракує в кожній мові, `i18n_translate` створює чернетку перекладу, яка йде на рев'ю |
| `git-sync` | опублікований контент дзеркалиться в Markdown із frontmatter; змінені файли повертаються changeset'ом (`aicms sync import`), тож pull request може наповнювати «Вхідні» |

Додано у фазі 3:

| Модуль | Що дає |
|---|---|
| `commerce` | товари й замовлення, публічний checkout, що рахує ціни на сервері, залишки, статуси замовлень з історією, `commerce_orders` / `commerce_set_status` / `commerce_stats`; потребує `payments` |
| `manual-payments` | дає `payments`: переказ або оплата при отриманні, людина позначає замовлення оплаченим |
| `stripe` | дає `payments`: Stripe Checkout, підписані вебхуки, повернення коштів |

Провайдери оплати повідомляють через подію `payment.updated`, тож заміна Stripe на іншого провайдера не зачіпає commerce.

Далі: `forms` · `reviews` · `redirects` · `analytics` · `workflows` (багатокрокові процеси агентів), векторний пошук і AI-інструменти для зображень.

### 6.4 Агент пропонує модуль
Агент може запропонувати встановити модуль. Пропозиція приходить у «Вхідні» як особливий changeset зі списком scopes і моделей, які просить модуль. Встановлює людина зі scope `modules:install` прямо з «Вхідних» (`cms_propose_module`, потім «Встановити»); агенти ніколи не ставлять код самі. Відхилена пропозиція закривається, а не повертається.

### 6.5 Реєстр

`docs/registry.json` (за адресою `https://malkovych.github.io/aicms/registry.json`) перелічує офіційні модулі й модулі спільноти разом із тим, що кожен заявляє: provides, requires, uses, scopes, маршрути, хуки. `aicms search <слова>` шукає модулі; `aicms add <name>` ставить модуль спільноти з npm і відмовляє, якщо його маніфест просить більше, ніж заявлено в реєстрі. Модулі спільноти додаються з термінала, де можна переглянути код; сервер ніколи не ставить їх сам, а агенти можуть пропонувати лише офіційні модулі. Щоб додати модуль у реєстр, відкрий pull request із його записом.

## 7. Як підключається агент

### 7.1 Входи

| Вхід | Для кого | Адреса | Фаза |
|---|---|---|---|
| **MCP** | Claude, Cursor, ChatGPT, будь-який MCP-клієнт | `POST /mcp` (Streamable HTTP) або `aicms mcp` (stdio) | 0 |
| **REST + OpenAPI** | function calling у будь-якій LLM, n8n, скрипти | `/api/v1/*`, `/openapi.json` | 0 |
| **Discovery** | будь-хто | `/llms.txt`, `/.well-known/aicms.json` | 0 |
| **Webhooks** | фронтенди, автоматизації | `webhooks` у конфігу | 0 |
| **SDK** | власні агенти | `@aicms/client` (TS), `aicms` (PyPI) | 1 |
| **SSE-події** | агенти, що реагують на зміни | `/api/v1/events` | 1 |
| **GraphQL** | фронтенди зі складними вибірками; посилання розгортаються в записи | `/graphql` | 2 ✓ |
| **A2A** | агент-до-агента: Agent Card і JSON-RPC, кожен Action — навичка | `/.well-known/agent-card.json`, `/a2a` | 3 ✓ |

### 7.2 Інструменти, які бачить агент

Агент бачить лише те, на що має права. MCP-інструменти мають підкреслення в назвах (`post_draft`), бо кілька LLM API не приймають крапки в назвах інструментів; у REST і коді Action так само зветься `post.draft`.

| Інструмент | Action | Що робить |
|---|---|---|
| `cms_describe` | `cms.describe` | моделі, поля, гайди, власні scopes і режим рев'ю агента |
| `cms_search` | `cms.search` | повнотекстовий пошук по доступних моделях |
| `<model>_list` | `<model>.list` | фільтр за індексованими полями, вибір полів, пагінація |
| `<model>_get` | `<model>.get` | один запис за `id` або унікальним полем, наприклад `slug`; `drafts: true` додає твої неопубліковані зміни |
| `<model>_draft` | `<model>.draft` | створити або змінити запис у changeset агента |
| `<model>_delete` | `<model>.delete` | запропонувати видалення запису |
| `cms_submit` | `cms.submit` | запустити перевірки й віддати changeset на рев'ю |
| `cms_changes` | `cms.changes` | changesets агента, результати перевірок і коментарі рев'юера |
| `cms_review` / `cms_merge` / `cms_reject` | `cms.review` … | для рев'юерів зі scope `changesets:review` |
| `cms_history` / `cms_restore` / `cms_revert` | `cms.history` … | версії запису; чернетка відновлення будь-якої версії або скасування злитого changeset |
| `cms_discard` | `cms.discard` | прибрати чернетки, які ще не надіслані |
| `cms_presence` | `cms.presence` | хто зараз переглядає чи редагує запис і чиї чернетки створять конфлікт |
| `cms_modules` / `cms_propose_module` | `cms.modules` … | встановлені модулі з їхніми правами, офіційні, які можна запропонувати; `cms_install_module` для адмінів (`modules:install`) |
| `cms_agents` / `cms_token` / `cms_revoke` / `cms_log` | `cms.agents` … | для адмінів (`agents:manage`, `events:read`): агенти, токени, журнал дій |
| `<module>_<action>` | `<module>.<action>` | Actions модулів |

### 7.3 Markdown на вході, блоки в базі
Агентам зручно читати й писати Markdown, людям потрібен візуальний редактор. AICMS зберігає блоки, а поле `blocks` приймає або масив блоків, або Markdown з блоками-директивами (`:::cta{href="/sale" label="До розпродажу"}`). Через MCP поля з блоками за замовчуванням повертаються як Markdown, через REST — як блоки. Дані ті самі, інтерфейс кожному свій.

### 7.4 Економія контексту
- `cms_describe` без аргументів дає коротку картину, з `{ model }` — детальну.
- Вибір полів: `post_get({ slug, fields: ["title", "slug"] })`.
- Компактні відповіді без службового шуму.

### 7.5 Шлях зміни від агента
1. **Підключення.** Агент приходить з токеном і отримує свій список інструментів.
2. **Знайомство.** `cms_describe` дає схеми, гайди й приклади.
3. **Чернетка.** Зміни пишуться в changeset, прод не чіпається.
4. **Перевірки.** `cms_submit` перевіряє схему, унікальність, посилання й конфлікти. Помилки повертаються агенту з назвами полів.
5. **Рев'ю.** Автоматично або людиною у «Вхідних» Studio (чи через `aicms changes`, `aicms merge`, `aicms reject`). Коментар до відмови агент бачить через `cms_changes` і подію `changeset.rejected`.
6. **Публікація.** Merge записує нові версії, подію в журнал і викликає вебхуки.
7. **Відкат.** Будь-яку версію запису можна відновити (`cms_restore` або «Історія» в Studio), а злитий changeset можна скасувати цілком (`cms_revert`). Обидві дії стають чернеткою й публікуються як будь-яка інша зміна, тож проходять перевірки, рев'ю й потрапляють у журнал.

## 8. Studio: для людини

Studio роздає саме ядро за адресою `/studio/`. Вхід — одноразове посилання з термінала (`aicms login`; `aicms dev` показує його під час запуску), яке перетворюється на сесійну cookie на 30 днів, тож пароля, який можна вкрасти, немає. Studio викликає ті самі Actions, що й агенти, через той самий конвеєр; її зміни потрапляють у журнал із входом `studio`.

Що є у фазі 1:

- **Вхідні.** Changesets від агентів: diff «було / стало» з точністю до слова, провалені перевірки, кнопки «Схвалити / Попросити правки» (коментар іде агенту) / «Закрити». Злитий changeset можна скасувати одним кліком.
- **Контент.** Списки й форми згенеровані зі схем: для кожного типу поля є свій ввід, поля з блоками мають Markdown-редактор із переглядом. Кожен запис має історію; будь-яку версію можна відкрити й відновити.
- **Агенти.** Scopes, режим рев'ю, використання бюджету, остання дія, незавершена робота. Видати токен (показується один раз разом із командою для MCP) або відкликати доступ.
- **Журнал.** Дії людей і агентів наживо через SSE.
- Англійська й українська, світла й темна теми, працює на телефоні.

Додано у фазі 2: **Медіа** (бібліотека із завантаженням перетягуванням і alt-текстом), **Модулі** (маніфести й встановлення одним кліком), пропозиції модулів у **«Вхідних»**, вибір файлу з бібліотеки у формах, панелі SEO й перекладів біля кожного запису.

Додано у фазі 3: **присутність**. Редактор показує, хто ще працює із записом, люди й агенти (агент, що готує зміну, видно як «редагує»), і попереджає, коли чиясь чернетка цього запису створить конфлікт.

Далі: **⌘K** (команди й звичайна мова: «знайди статті без обкладинки» → `post.list` з фільтром), спільне редагування з Yjs, блоковий редактор поруч із live preview фронтенду, ролі для людей, окрім власника.

| Адаптер | Що дає | Стан |

| `@aicms/next` | читання з кешем і тегами на модель, `revalidateTag` з вебхуків, `<Blocks />` для Server Components | фаза 1 ✓ (Draft Mode preview далі) |
| `@aicms/astro` | Content Layer loader з готовим HTML блоків | фаза 1 ✓ |

| `@aicms/sveltekit` | load-хелпери на `fetch` SvelteKit з `depends`, заголовки кешу, живий `invalidate` після публікації | фаза 2 ✓ |
| `@aicms/react-router` | loaders для React Router 7 / Remix | пізніше |
| `@aicms/angular` | сервіси й резолвери | пізніше |
| `@aicms/expo` | мобільний клієнт з офлайн-кешем | пізніше |

Спільне для всіх: клієнт, типізований зі схем (`aicms types`), компонент `<Blocks />` або `blocksToHtml`, а згодом компонент зображень і оверлей візуального редагування.

```tsx
// lib/cms.ts
import { createAicms } from "@aicms/next"
import type { Schema } from "./aicms-types"            // npx aicms types --out lib/aicms-types.ts
export const cms = createAicms<Schema>({ url: process.env.AICMS_URL! })

// app/blog/[slug]/page.tsx
import { Blocks } from "@aicms/next"
import { cms } from "@/lib/cms"

export default async function Post({ params }) {
  const post = await cms.post.get({ slug: (await params).slug })   // тип із models/post.ts
  return <Blocks value={post.body} />
}
```

Режими розгортання:
- **Вбудований:** AICMS монтується як route handler усередині Next.js / Nuxt / SvelteKit, один деплой.
- **Окремий:** `aicms start` або Docker-образ.
- **Edge:** Cloudflare Workers + D1 + R2: `export default createWorker(config)` з `aicms/edge`, Studio з Workers Assets, токен власника із секрету (`examples/edge`).

## 13. Рішення

| Питання | Рішення |
|---|---|
| Контент у базі чи в git? | Джерело правди — база: її потребують changesets, права до поля, паралельні агенти й транзакції. Модуль `git-sync` дзеркалить опублікований контент у Markdown + frontmatter і перетворює pull request на changesets, тож розробники й агенти-кодувальники все одно можуть працювати через git. |
| Чи може агент запропонувати модуль? | Так, через «Вхідні», з показаними правами. Встановлює людина. |
| Python SDK | Зроблено у фазі 1 разом з TypeScript SDK: `sdk/python`, лише стандартна бібліотека. |
| Ліцензія | MIT для всього: ядра, SDK, адаптерів і офіційних модулів. Безкоштовно для будь-якого використання, зокрема комерційного. Якщо колись знадобиться фінансування, воно буде через донати, а не через платну версію. |
